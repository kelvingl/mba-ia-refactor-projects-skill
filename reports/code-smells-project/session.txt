  ================================                                                        
  ARCHITECTURE AUDIT REPORT
  ================================                                                                                                             
  Project: code-smells-project
  Stack:   Python + Flask 3.1.1                                                                                                                
  Files:   4 analyzed | ~784 lines of code                                                                                                   
                                                                                                                                             
  ## Summary
  CRITICAL: 5 | HIGH: 4 | MEDIUM: 4 | LOW: 2

  ## Findings

  ### [CRITICAL] SQL Injection
  **File:** `models.py:28, 47-50, 57-60, 65-67, 92, 109-111, 126-129, 140, 148-150, 163-165, 174, 188, 192, 279-282, 289-298`
  **Description:** Virtualmente todas as queries no módulo são construídas por concatenação de strings com dados externos. Exemplos:
  `cursor.execute("SELECT * FROM produtos WHERE id = " + str(id))` (linha 28); `cursor.execute("SELECT * FROM usuarios WHERE email = '" + email
   + "' AND senha = '" + senha + "'")` (linha 109–111); `query += " AND (nome LIKE '%" + termo + "%'..."` (linha 289). Os parâmetros vêm de
  `request` via controller.
  **Impact:** SQL injection completo — qualquer chamador pode exfiltrar todo o banco, bypassar autenticação com `' OR 1=1--`, ou destruir
  dados.
  **Recommendation:** substituir todas as queries por prepared statements: `cursor.execute("SELECT * FROM produtos WHERE id = ?", (id,))`.

  ### [CRITICAL] Hardcoded Credentials
  **File:** `app.py:7`, `controllers.py:289`
  **Description:** `app.config["SECRET_KEY"] = "minha-chave-super-secreta-123"` literal no código. A mesma string é retornada publicamente em
  `/health` como `"secret_key": "minha-chave-super-secreta-123"` (controllers.py:289).
  **Impact:** a chave está versionada no Git e exposta via HTTP — qualquer pessoa pode forjar sessões. Após publicada, é irrevogável sem
  deploy.
  **Recommendation:** mover para variável de ambiente `FLASK_SECRET_KEY` em `src/config/settings.py`; boot deve falhar se ausente. Remover o
  campo da resposta de `/health`.

  ### [CRITICAL] Plaintext Password Storage
  **File:** `models.py:109-111, 122-131`, `database.py:75-83`
  **Description:** `criar_usuario` insere a senha sem hash (linha 127). `login_usuario` compara senha em texto plano via SQL (linhas 109-111).
  O seed popula o banco com senhas literais como `"admin123"` (database.py:75-83). `get_todos_usuarios` retorna o campo `senha` em texto plano
  no JSON (models.py:80-86).
  **Impact:** qualquer vazamento do banco expõe todas as credenciais imediatamente. Viola LGPD/GDPR.
  **Recommendation:** usar `werkzeug.security.generate_password_hash` na criação e `check_password_hash` no login. Nunca retornar o campo de
  senha em nenhuma resposta.

  ### [CRITICAL] Endpoint de Execução Arbitrária de SQL
  **File:** `app.py:47-78`
  **Description:** `/admin/reset-db` (linha 47) apaga todas as tabelas sem autenticação. `/admin/query` (linha 59) recebe `"sql"` no corpo e
  executa `cursor.execute(query)` diretamente — qualquer instrução SQL, sem restrição.
  **Impact:** qualquer pessoa na rede pode apagar todo o banco ou exfiltrar qualquer dado com um único POST sem credenciais.
  **Recommendation:** remover ambos os endpoints completamente. Utilitários de diagnóstico devem ser scripts CLI, nunca rotas HTTP.

  ### [CRITICAL] Debug Mode Habilitado em Produção
  **File:** `app.py:8, 88`, `controllers.py:283-290`
  **Description:** `app.config["DEBUG"] = True` (linha 8) e `app.run(debug=True)` (linha 88) são incondicionais. `/health` retorna `"debug":
  True` e `"ambiente": "producao"` simultaneamente (controllers.py:283-290).
  **Impact:** reloader e debugger interativo Flask expostos; stack traces completos chegam ao cliente; combinação com debugger PIN pode levar a
   RCE.
  **Recommendation:** `app.config["DEBUG"] = os.getenv("FLASK_DEBUG","false").lower()=="true"`. Remover campos de diagnóstico do output de
  `/health`.

  ---

  ### [HIGH] Authentication Absent
  **File:** `app.py:1-88`, `controllers.py:128-134, 188-220, 222-227`
  **Description:** `/login` retorna dados do usuário mas **não emite nenhum token** — não existe `jwt.encode` no código. Nenhum middleware de
  autenticação existe. Todas as rotas estão abertas sem verificação. `criar_pedido` aceita `usuario_id` do corpo (controllers.py:195) e
  `listar_pedidos_usuario` usa o id do path sem comparar com identidade autenticada (controllers.py:222-227).
  **Impact:** qualquer cliente anônimo acessa dados de todos os usuários (incluindo senhas), modifica pedidos alheios e cria pedidos em nome de
   qualquer usuário.
  **Recommendation:** JWT deny-by-default (T-15): guard global com allowlist de rotas públicas, segredo obrigatório no boot, identidade
  extraída do token, checagem de dono no controller.

  ### [HIGH] God Module
  **File:** `models.py:1-315`
  **Description:** 315 linhas misturando acesso ao banco (queries SQL), lógica de negócio (cálculo de descontos progressivos em
  `relatorio_vendas` linhas 256-263; validação de estoque e orquestração transacional em `criar_pedido` linhas 139-167) e serialização
  (dicionários montados manualmente em cada função).
  **Impact:** impossível testar lógica de desconto sem banco real; qualquer mudança de serialização exige editar o mesmo arquivo que controla
  transações.
  **Recommendation:** separar em `src/models/` (schema/acesso a dado), `src/controllers/` (orquestração) e helpers de serialização/DTOs.

  ### [HIGH] Global Mutable State
  **File:** `database.py:4-12`
  **Description:** `db_connection = None` é variável global de módulo reatribuída com `global db_connection` em `get_db()`. A conexão é
  compartilhada entre todas as requisições; `check_same_thread=False` desabilita a proteção do SQLite em vez de resolver o problema.
  **Impact:** condição de corrida sob carga concorrente; testes não isolam estado entre chamadas.
  **Recommendation:** usar `flask.g` para escopo de conexão por requisição, ou repositório com injeção de dependência.

  ### [HIGH] Missing Centralized Error Handling
  **File:** `controllers.py:5-292`
  **Description:** cada uma das 14 funções tem `try/except Exception as e` retornando `jsonify({"erro": str(e)})`. Não existe middleware de
  erro global. A exceção é serializada e enviada ao cliente, incluindo mensagens internas do SQLite.
  **Impact:** formato de erro inconsistente; mensagens do banco chegam ao cliente; ~30 linhas duplicadas de tratamento.
  **Recommendation:** handler global `@app.errorhandler(Exception)` que loga internamente e retorna mensagem genérica; exceções tipadas para
  controle de fluxo.

  ---

  ### [MEDIUM] N+1 Query
  **File:** `models.py:171-200, 203-233`
  **Description:** `get_pedidos_usuario` e `get_todos_pedidos` abrem cursor de pedidos e, para cada linha, cursores adicionais para
  `itens_pedido` (linhas 187-188) e nome do produto por item (linhas 192-193). Para N pedidos com M itens: `1 + N + N*M` queries.
  **Impact:** latência cresce linearmente; em produção com centenas de pedidos o endpoint se torna inviável.
  **Recommendation:** único JOIN: `SELECT p.*, ip.*, pr.nome FROM pedidos p JOIN itens_pedido ip ON ip.pedido_id = p.id JOIN produtos pr ON
  pr.id = ip.produto_id WHERE p.usuario_id = ?`.

  ### [MEDIUM] Missing Pagination
  **File:** `models.py:6-22, 203-233`
  **Description:** `get_todos_produtos()` executa `SELECT * FROM produtos` sem `LIMIT`/`OFFSET` (linha 7); `get_todos_pedidos()` idem (linha
  206). Nenhum endpoint aceita `?page=` ou `?limit=`.
  **Impact:** com crescimento da base, respostas ilimitadas degradam performance do banco e saturam memória.
  **Recommendation:** `LIMIT ? OFFSET ?` com `page`/`per_page` nos query params, defaults razoáveis (ex.: `per_page=20`).

  ### [MEDIUM] Duplicated Validation Logic
  **File:** `controllers.py:24-55, 64-92`
  **Description:** validação de campos de produto (nome, preço, estoque, comprimento, categoria válida) é copiada integralmente entre
  `criar_produto` e `atualizar_produto`. A lista `categorias_validas` é um literal repetido.
  **Impact:** regra diverge silenciosamente quando corrigida em um handler e esquecida no outro.
  **Recommendation:** schema compartilhado (Marshmallow/Pydantic) ou função `validar_payload_produto(dados)` reutilizada pelos dois handlers.

  ### [MEDIUM] Referential Integrity Broken
  **File:** `models.py:65-70`, `database.py:14-52`
  **Description:** `deletar_produto` faz `DELETE FROM produtos WHERE id = ?` sem remover linhas dependentes em `itens_pedido`. O schema não
  define `FOREIGN KEY` nem `ON DELETE CASCADE`.
  **Impact:** itens de pedidos existentes ficam com `produto_id` órfão; consultas futuras retornam `"Desconhecido"` silenciosamente
  (models.py:194).
  **Recommendation:** `FOREIGN KEY(produto_id) REFERENCES produtos(id) ON DELETE RESTRICT` ou soft-delete com campo `ativo`.

  ---

  ### [LOW] Log via print
  **File:** `controllers.py:8, 106, 161, 179, 208-210, 247-250`
  **Description:** informações operacionais emitidas via `print()` puro sem nível, timestamp ou estrutura.
  **Impact:** impossível filtrar ruído em produção; sem timestamp, correlação de eventos é impossível.
  **Recommendation:** `import logging; logger = logging.getLogger(__name__)` com `logger.info()` / `logger.error()`.

  ### [LOW] request.get_json() Without silent=True (OBS-04)
  **File:** `controllers.py:26, 66, 148, 169, 190, 239`, `app.py:61`
  **Description:** `request.get_json()` chamado sem `silent=True` em 7 pontos. No Flask ≥ 2.3, body não-JSON lança `BadRequest` não tratada,
  vazando stack trace ao cliente.
  **Impact:** requisição com body malformado gera resposta interna do Werkzeug antes do handler da aplicação.
  **Recommendation:** `request.get_json(silent=True)` + verificar `if dados is None` explicitamente.
